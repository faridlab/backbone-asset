# Council — module:backbone-asset — focus: ops-ux-security-readiness

## Best call
**Module-level verified-principal contract: strip `company_id` from trust in the request body and make the engine derive tenant from an authenticated `AuthPrincipal`, fail-closed.** Concretely, in `backbone-asset` this release: (1) `asset_lifecycle_handler.rs` handlers read `company_id` from an axum `Extension<AuthPrincipal>` (set by the consumer's auth middleware), never from `RegisterAssetRequest`/`DepreciateAssetRequest`/`DisposeAssetRequest`; where a body `company_id` still appears for backward-compat it is **asserted equal** to the principal's company on mismatch → 403, not used as the source of truth; `ActivateAssetRequest` gains the principal-derived company it currently lacks entirely. (2) `load_asset` (`asset_write_service.rs:244`) grows a `company_id: Uuid` parameter and scopes `find_snapshot` by it — the ID-only "ride the caller's scope" pattern is removed; cross-tenant read becomes NotFound. (3) The in-tx `bind_company_on` at `asset_activate.rs:96` (and siblings) becomes a defensive **assert** (bind value == principal company, else rollback + 4xx), not the authoritative source. (4) Fail-closed default: no `AuthPrincipal` on the request → 401, configurable open-mode only behind a non-default feature flag for the event/job path. Update ADR-0008 to record that the body/row is no longer a trusted tenant origin.

Consumer wiring (`company_auth` middleware + flip to `rls_app_role` in `backbone-application`) is the **required activator**, ranked #2 below — but it is not the Best call, for three reasons: the chair's authority is this module's contract, not the consumer's; skeptic proved consumer-only is insufficient because the engine's in-tx re-bind defeats any upstream GUC; and shipping the module fix as fail-closed converts "optional future auth" into a hard deployment dependency, which is exactly the pressure required.

- **Residual negative value:** ~1–2 sprint cross-team coupling (module fails closed on the day it ships; `backbone-application/src/main.rs:257-287` must wire `company_auth` + non-superuser role in the same release window or every lifecycle route 401s in prod — which is the *correct* failure, but a coordination cost). Plus a contract break for any existing caller passing body `company_id`: the event/job path (`run_depreciation`/`dispose_asset` signatures from ADR-0008) must keep an explicit `company_id` param for non-HTTP contexts, so the contract forks between HTTP (principal-derived) and event (explicit) entry points — measurable as one extra validation layer to maintain, ~tens of lines.
- **Reversibility:** **Easy at the code level** (the contract is a few handler signatures + one `load_asset` param); **one-way door operationally** — once fail-closed ships, consumers cannot bypass without a feature flag, which is the intended effect.
- **What would flip this:** Evidence that the engine can be made to **not** call `bind_company_on` inside the tx on the HTTP path (letting the consumer's GUC stay authoritative) *without* breaking the event/job path that has no middleware. That is not achievable without forking the scope mechanism per entry-point — i.e., it collapses back into this same fix. No cheaper alternative exists; the body is an attacker-controlled input and `load_asset` is an unfenced read oracle, full stop.

## Disagreement map
1. **Where the tenant boundary is enforced — module vs. consumer.** Steelman holds the engine's three fences + `company_scope` suffice if the consumer sets `app.company_id`. Skeptic + devopssec hold the body/row is untrusted and `load_asset` is a cross-tenant oracle. **Crux:** `asset_activate.rs:96` proves the engine re-binds the tx to an unverified value *inside* the tx, overwriting any upstream GUC — so consumer RLS alone cannot close it. **Resolution: module fix wins; steelman's position is refuted by the code.**
2. **Release scope — close-the-hole vs. harden-ops.** yagni-business says ship auth + non-superuser role now, defer job-runner/observability. operational-realist wants the synchronous depreciation loop moved to a job path with timeout, plus tracing spans, metrics, and rate-limiting in the same release. **Crux:** the focus lens is security-readiness and the exploit is live; ops hardening is real but does not touch the write oracle. **Resolution: yagni wins; ops work parks.**
3. **`load_asset` semantics — clean port vs. read oracle.** ddd-bounded-context defends ID-only load as a tidy port that defers scoping to the caller. contract-seat + skeptic call it a cross-tenant enumeration primitive. **Crux:** "ride the caller's scope" assumes a caller scope exists; in the live deployment there is none (superuser). **Resolution: `load_asset` must take the verified company and scope by it; the port stays clean, the assumption becomes explicit.**

## Maturity scorecard
(scored on each seat's OWN axis, 1–5)
- **devopssec (security):** 2/5 — engine cryptography is genuinely strong, but the module trusts a body-supplied `company_id` and `load_asset` is an unfenced cross-tenant read; deployment runs as superuser with `company_auth` unwired.
- **operational-realist (ops):** 2/5 — no tracing spans, no metrics, no rate-limiting on lifecycle handlers; depreciation is a synchronous for-loop of GL posts per request with no timeout or job path.
- **domain-expert (financial integrity):** 4/5 — three tenant fences, deterministic GL dedup, row-lock serialization, DB CHECK invariants, post-then-gate ordering; one availability coupling (synchronous GL post → 424 if accounting is down).
- **ddd-bounded-context (boundary discipline):** 3/5 — ports are tidy, but `load_asset`'s "ride the caller's scope" embeds a consumer assumption into the module and `company_id`-in-the-body crosses the trust boundary inward.
- **contract-seat (API contract safety):** 2/5 — `company_id` is an unverified input treated as authoritative on three of four lifecycle verbs; `ActivateAssetRequest` has no tenant claim at all; contract is unsafe-by-default and requires the consumer to compensate.
- **steelman (strongest-case / engine internals):** 4/5 — the engine's math, fencing, and dedup are the strong dimension; the weakness is environmental (deployment + handler trust), not in the engine's financial logic — which is precisely why the fix belongs at the handler contract, not the engine internals.

## Parking lot
- **Depreciation job-runner + timeout** (operational-realist) — real availability cliff, out of focus for the security release; revisit after #1/#2 land.
- **Tracing spans + metrics on lifecycle handlers** (operational-realist, devopssec) — defer to the ops-hardening sprint; no security impact.
- **Rate-limiting on register/depreciate/dispose** (devopssec) — abuse-control, not boundary-control; park until telemetry from the post-fix deployment justifies thresholds.
- **Synchronous GL post → 424 availability coupling** (domain-expert) — architectural; belongs in the event-sourcing/outbox discussion, not this council.
- **gRPC/OpenAPI feature-gate coverage** (not raised by any seat) — not in the ops-ux-security-readiness lens.
